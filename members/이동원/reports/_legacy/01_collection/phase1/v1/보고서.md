## 1. 목적 (Why)

### 1.1 이 작업이 왜 필요한가

전체 파이프라인 (corp_code 매핑 → rcept_no 조회 → document.xml 다운로드 → 섹션 추출 → ESG passage 후보 → log 기록) 을 **1건의 firm-year에서 검증**한다. 검증 통과 후 5/16부터 Phase 2 batch(50건 → 381 firm-year)로 확장.

### 1.2 분석 가설과의 연결

본 프로젝트의 핵심 가설은 **"사업보고서의 ESG 언어(공시 의도) → KCGS ESG 등급(외부 평가)"**. 이 가설 검증의 출발점은 **공시 원문에서 ESG 언어를 정확히 추출**하는 것. Phase 1 파일럿은 추출 파이프라인 자체가 작동하는지 확인하는 단계 — quality는 다음 단계(전처리)에서 끌어올림.

  - v0.3 COLLECTION 가이드 "API key 안전 (강화)" 탭 (`mask_key()` 패턴)

- **벤치마킹**: 강의 Week 4 (requests 기본) · 공개코드 dart-fss `_dart_fss.py`의 .env 로딩

### 3.2 Step 2 · 파일럿 대상 설정

- **근거**: 가이드 02 line 31-35 · line 35 (회사명 join 위험) · line 38 (esg_year 매핑) · line 117 (381)
- **벤치마킹**: 실무 ETL 패턴 (입력 형식 사전 검증 → 이후 단계 에러 조기 발견)

### 3.3 Step 3 · stock_code → corp_code (corpCode.xml)

- **What**: `corpCode.xml` 1회 다운로드 → DataFrame → parquet 캐시. 005930 → 00126380 매핑 확인
- **Why**: 가이드 02 line 153 "1. stock_code로 corp_code". 캐시로 5/19까지 재사용 (위반금지 5)
- **근거**: 가이드 02 line 28, 153 · 공개코드 dart-fss `_dart_fss.py`의 corpCode 캐시 패턴 · opendart-py 동일 패턴

### 3.4 Step 4 · corp_code → rcept_no (list.json)

- **What**: `list.json` 호출 (params: corp_code, bgn_de=20250101, end_de=20251231, pblntf_detail_ty=A001, last_reprt_at=Y) → 사업보고서 (2024.12) 필터 → rcept_no + viewer_url

- **근거**: 가이드 02 line 154, 69, 216-249 (직접 API Python 예시 코드 그대로 적용)
- **벤치마킹**: 가이드 코드 + 실무 ETL (status 분기 — FAIL_HTTP / FAIL_LIST / FAIL_RCEPT 별도 분류)

### 3.5 Step 5 · document.xml 다운로드 (raw zip)

- **What**: `document.xml` API 호출 → zip 저장 (`data/raw/005930_2024_disclosure.zip`) → XML 텍스트 추출. 캐시 hit (>1KB) 시 재다운로드 X
- **Why**: 가이드 02 line 155 "3. document.xml로 raw ZIP" + line 94 "document.xml이 표준 raw 텍스트 경로 (viewer 우회 ❌)" (위반금지 2). raw 보관해야 5/19 게이트 G6 (viewer ↔ 추출 정합성) 검증 가능
- **근거**: 가이드 02 line 155, 94, 253-274 · 위반금지 2
- **벤치마킹**: 가이드 코드 (zipfile.ZipFile + BytesIO) · 실무 ETL (size 기반 캐시 hit 판단)

### 3.6 Step 6 · XML → 텍스트 + II/IV/VI 섹션 추출

- **What**: `strip_tags()` (lxml + 정규식 fallback) → 정규식으로 II/III/IV/V/VI/VII 헤딩 위치 식별 → II, IV, VI 텍스트 발췌 → sections.json 저장

- **벤치마킹**: 공개코드 dart-fss · Li 2021 RFS
- **한계 메모 (Q4-a 중)**: III/V/VII는 다음 섹션 시작점 식별용. 회사가 헤딩을 누락하거나 다른 표현 사용 시 누락 가능 → v2에서 alt 패턴 추가

### 3.7 Step 7 · ESG passage 후보 추출 (seed_dictionary)

### 4.2 정성 결과 — v1 실패 진단

- **핵심 원인**: zip 안 3개 XML 중 첫 번째(`ACODE=00761`)는 **연결감사보고서**였음. 사업보고서 본문 (II 사업의 내용 / IV 임원의 보수 / VI 그 외 참고사항)이 들어있는 파일은 3번째 (`20250311001085.xml`, 5,780,877자). 코드가 `zf.namelist()[0]`만 읽어서 본문 자체를 못 봄
- **부차 원인 1 — `.env` 경로 fragile**: `Path('..').resolve().parent.parent`가 cwd 의존. Jupyter cwd에 따라 ROOT가 잘못 잡힘 → 사용자가 직접 `find_project_root()`로 수정 (이미 노트북에 반영됨)
- **부차 원인 2 — log 스키마 evolution 미대응**: `viewer_url` 컬럼 추가로 9 → 10컬럼이 됐는데 기존 파일을 그냥 append → `pd.read_csv` 시 ParserError
- **부차 원인 3 — 진단 출력 부재**: 0건이 나와도 어디서 막혔는지 출력 안 함 → 원인 추적까지 시간 소요

## 5. 한계 · 위험

### 5.1 알려진 한계

- **1건의 파일럿만으로는 일반화 불가** — Samsung은 대기업이라 IR이 잘 정리됨. 중소·중견 기업에서는 정규식 패턴 누락 가능성 ↑
- **섹션 헤딩 정규식 3개 변형만** — `II`, `Ⅱ`, `2` 외 다른 표현 (`Part II`, `제2장`) 누락 가능 → v2 alt 셀로 추가
- **문장 분리 단순** — `re.split('[.?!]')` + 줄바꿈만 사용. KSS 같은 한국어 문장 분리기 미사용 → 02 전처리에서 보강
- **seed_dictionary 30개만** — 가이드 02 line 75-94의 예시 키워드 외 ESG 신조어 누락 가능 → 02 전처리에서 확장

### 5.2 다음 버전(v2)에서 개선할 점

- alt 셀 추가: 정규식 패턴 3종 비교 (Step 6)
- alt 셀 추가: passage min_len 비교 (20 vs 30 vs 50)
- alt 셀 추가: last_reprt_at='Y' vs 'N' (정정공시 영향 측정)
- KSS 또는 더 정교한 한국어 문장 분리기 도입

### 5.3 위반금지 8항목 self-check (Step 10 표 요약)

본 노트북 Step 10에 상세표 있음. 8개 모두 ✅ 확인 후 commit.

### 5.4 위험 시나리오

- **OpenDART rate limit (HTTP 429)** — `time.sleep(0.5)` + try/except로 대응. 1건이라 발생 가능성 낮지만 Phase 2 batch에서 주의
