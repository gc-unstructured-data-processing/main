## 1. 목적 (Why)

### 1.1 v2의 본질적 실패 진단 → v3의 존재 이유

v2는 "passage 23건 추출 / V·VI 섹션 매칭"이라는 표면적 성공을 보였으나, **사용자(이동원) viewer 정합성 검증 결과 0/5 일치** — 추출된 모든 문장이 원문(사업보고서 VI "이사회 등 회사의 기관에 관한 사항")에 존재하지 않음. 진단:

1. **zip 안 3개 XML을 그냥 concat한 것이 문제의 시작점** — Fix #2가 "다중 파일 처리"라는 표면적 문제만 해결했고 사업보고서·감사보고서·연결감사보고서를 한 corpus에 섞었음
2. **정규식이 가장 먼저 등장하는 매칭을 잡는 특성상** 연결감사보고서의 "감사인"·"이사회 귀중"이 V·VI로 잘못 라벨링됨 → 사업보고서 본문 안 진짜 II/IV/VI는 검색조차 못 함
3. **viewer 검증을 통한 견제(위반금지 #3)에서 발각됨** — 가이드 line 94 "MCP/추출 결과 그대로 신뢰 ❌, 반드시 코드 재현 + viewer URL 확인"
4. **추출된 23건의 passage는 사실상 감사보고서 노이즈** — Phase 2 batch로 가면 corpus 전체가 오염될 위험

본 v3의 목적: 위 4개 fix + 5개 정밀 세분화 적용 후 **viewer ≥ 4/5 일치 + passage ≥ 150건 + 차원 균형 확보** 후 Phase 2 진입.

### 1.2 분석 가설과의 연결

본 프로젝트 가설: **"사업보고서의 ESG 언어(공시 의도) → KCGS ESG 등급(외부 평가)"**. 이를 검증하려면 **사업보고서 본문**의 ESG 표현을 정확히 추출해야 하며, 감사보고서의 감사인 의견은 가설의 입력 변수가 아님. v3는 가이드 line 18 ("우리가 찾는 내용은 사업보고서의 II, IV, VI 섹션에 담긴 ESG 관련 표현")을 글자 그대로 구현.

### 3.1 Fix #0 · 사업보고서 본문 XML만 ESG primary로 사용 (Step 5) — 🚨 v3 핵심 신규

**v2 문제** (viewer 0/5 진단 결과):
v2는 zip 안 3개 XML을 `\n\n`으로 그냥 concat → 정규식이 가장 먼저 등장하는 매칭(=연결감사보고서)을 V·VI로 잘못 라벨링. 사업보고서 본문은 검색 대상에서 빠짐.

**v3 해결:**
```python
def split_zip_by_document_type(zip_bytes: bytes) -> dict:
    """zip 안 모든 XML을 DOCUMENT-NAME으로 type 판별 → type별 dict 반환."""
    import re
    sources = {'사업보고서': [], '연결감사보고서': [], '감사보고서': [], 'unknown': []}
    with zipfile.ZipFile(BytesIO(zip_bytes)) as zf:
        for name in zf.namelist():
            xml_text = zf.read(name).decode('utf-8', errors='ignore')
            m = re.search(r'<DOCUMENT-NAME[^>]*>([^<]+)</DOCUMENT-NAME>', xml_text)
            doc_type = m.group(1).strip() if m else 'unknown'
            if doc_type not in sources:
                sources['unknown'].append((name, xml_text, doc_type))
            else:
                sources[doc_type].append((name, xml_text, doc_type))
    return sources

# 사업보고서 본문 (primary)
primary = sources['사업보고서']
if not primary:
    raise RuntimeError("FAIL_NO_BUSINESS_REPORT")  # 위반금지 #1: 가짜 0 채우지 말 것
primary_name, primary_xml, _ = max(primary, key=lambda x: len(x[1]))  # 가장 큰 파일

# 보조 (raw 보존 — 세분화 축 A)
aux_consolidated = sources['연결감사보고서']  # 별도 json
aux_separate = sources['감사보고서']  # 별도 json
```

### 3.2 Fix #2 · strip_tags 무손실 보강 (Step 6) — 🚨 P0

**v2 문제**: XML 6.93M → 텍스트 95.2K (압축률 1.4%) — 단순 정규식 `<[^>]+>`이 CDATA·중첩 노드에서 손실 의심.

**v3 해결:**
```python
def strip_tags_v3(xml_text: str) -> tuple[str, dict]:
    """lxml.itertext()로 무손실 추출 + 단계별 길이 가시화."""
    diag = {'xml_length': len(xml_text)}
    try:
        parser = etree.XMLParser(recover=True, huge_tree=True)
        root = etree.fromstring(xml_text.encode('utf-8'), parser=parser)
        text = ' '.join(root.itertext())
        diag['method'] = 'lxml_itertext'
    except Exception as e:
        # fallback — 정규식
        text = re.sub(r'<[^>]+>', ' ', xml_text)
        diag['method'] = 'regex_fallback'
        diag['error'] = str(e)
    text = re.sub(r'\s+', ' ', text).strip()
    diag['text_length'] = len(text)
    diag['compression_rate'] = diag['text_length'] / diag['xml_length']
    return text, diag
```

**검증 기준**: Samsung 사업보고서 본문 텍스트 ≥ 1.15M자 (압축률 ≥ 20%).
**근거**: 가이드 line 156 + dart-fss `parsers/disclosure.py` lxml 패턴.

## 부록 B · 가이드 line 250-261 예시 코드와 v3의 차이

가이드 line 250-261에는 다음 예시 코드가 있음:
```python
with zipfile.ZipFile(BytesIO(res.content)) as zf:
    first_name = zf.namelist()[0]
    xml_text = zf.read(first_name).decode("utf-8", errors="ignore")
```

이 예시 코드를 그대로 따라하면 v1·v2처럼 첫 번째 파일(연결감사보고서)만 잡힘. 하지만 가이드의 **의도(line 18 "사업보고서의 II, IV, VI 섹션")** 와는 다른 결과. v3는 가이드 예시 코드를 **위반하는 게 아니라 가이드 의도를 정확히 구현**하기 위해 DOCUMENT-NAME 기반 type 판별로 보강. 가이드 line 94의 "MCP/LLM 추출 결과 그대로 신뢰 ❌"의 정신을 예시 코드에도 동일하게 적용 — 즉 예시 코드를 그대로 신뢰하지 않고 viewer로 검증해 보완.
